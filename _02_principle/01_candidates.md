## 3. 逐方案原理阐述

### Q1-S1 纯 LLM 直出

- **原理**：prompt = 意图 + 平台/shell 信息 + 少量示例，模型一次补全输出命令文本；输出直接作为提案。
- **能力边界**：实现最薄、冷启动零依赖；但命令正确性完全依赖模型训练记忆。工具版本更迭（flag 改名/废弃）时模型知识漂移；长尾参数组合易出现"语法正确但参数不存在"的幻觉；无法解释"为什么是这个参数"以外的参数来源。
- **风险与对策**：幻觉命令静默失败（概率中/影响中）→ 执行闸门只能拦已知危险模式，拦不住"无害但错误"；版本漂移（概率高/影响低）→ 无解，需 S2 兜底。**结论：只能作为降级路径，不能作为主路径。**

### Q1-S2 LLM + 命令知识 grounding

- **原理**：先经本地命令知识库（对 `--help`/man 文本做结构化解析得到的 ParamSpec 集合，附 AI 补全与人工验证标记）召回目标命令的参数 schema，注入 prompt 约束生成空间；LLM 输出 JSON 结构化提案，经 schema 校验（参数必须在已注册集合内），未命中知识时降级 S1 并把结果标记 unverified。
- **能力边界**：首次遇到陌生命令需一次解析成本（执行 `--help` 或读 man）；解析器对非标准 help 格式覆盖率有限（Go/Cobra 风格、GNU 风格较标准，手工格式参差）；grounding 只约束参数合法性，不保证语义正确（语义仍靠模型）。
- **风险与对策**：help 格式千奇百怪解析失败（概率中/影响低）→ 降级 S1 + 标记 unverified，用户确认即是反馈回路；知识库膨胀（概率低/影响低）→ 按 command+platform 缓存、LRU 淘汰。

### Q1-S3 纯规则模板库

- **原理**：人工维护"意图特征 → 命令模板"映射表，匹配即得命令。
- **能力边界**：确定性 100%、零延迟、零成本；但自然语言开放性使模板覆盖率永远不足，长尾意图全部漏接，维护成本随覆盖线性增长。
- **风险与对策**：覆盖率不足（必然）→ 仅吸收其思想：用户确认过的高频提案可固化复用（与方案库合流），不作为独立机制建设。**结论：不单独采用。**

### Q2-S1 静态错误映射库

- **原理**：对 exit code（127 命令未找到、126 无执行权限、13 权限拒绝…）与高频 stderr 模式（`No such file or directory`、`Permission denied`…）建映射表，命中即出解释。
- **能力边界**：零成本、离线、毫秒级、确定性；但只覆盖"通用错误"，对具体命令语义错误（如 git 冲突细节）覆盖趋零。
- **风险与对策**：覆盖率低（必然）→ 作为确定性快速通道，未命中走 S2。

### Q2-S2 LLM 上下文诊断

- **原理**：诊断 prompt = 失败命令 + 完整 stderr + 退出码 + cwd/平台/shell + 最近 N 条相关执行记录，要求模型输出结构化诊断：根因假设必须引用 stderr 原文片段作证据、给置信度、给修复提案列表。
- **能力边界**：诊断质量上限取决于模型；依赖后端可用性；上下文窗口限制长 stderr（截断保头部+尾部错误行）。
- **风险与对策**：幻觉根因（概率中/影响中）→ 强制"证据引用"结构（无 stderr 引用的假设标记 speculation）、置信度排序；后端不可用（概率低/影响中）→ 降级 S1 快速通道 + 明确报错。

### Q3-S1 SQLite（WAL）

- **原理**：单文件关系库；WAL 模式下读写不互锁（多客户端读 + 单写者），事务保证追加式审计与会话事件的原子性；索引支撑时间/目录/命令多维度检索。
- **能力边界**：个人规模（十万行级）绰绰有余；需要 SQL 与迁移机制；全文检索默认 LIKE，FTS5 可后续启用。
- **风险与对策**：SQL 样板（必然/影响低）→ storage Adapter 提供薄原语，SQL 归属各 data 方法。

### Q3-S2 嵌入式 KV

- **原理**：按 key 读写 value，无服务进程。
- **能力边界**：写入快、嵌入简单；但历史检索需"时间/目录/命令/状态"多条件组合，KV 无二级索引，须自建倒排，等于重写半个数据库。
- **风险与对策**：查询能力缺失（必然/影响高）→ 不采用。

### Q3-S3 JSON 文件集

- **原理**：每记录一个 JSON 文件，目录扫描即查询。
- **能力边界**：零依赖、人可直接看文件；万条级扫描慢、无原子批量写、并发写靠文件锁脆弱、无索引。
- **风险与对策**：规模与并发均不可持续（概率高/影响高）→ 不采用（仅方案库导出格式沿用 JSON 文件）。

### Q4-S1 仅 CLI 文本协议

- **原理**：Agent 以子进程方式调用 `iac` 子命令，从 stdout 文本中解析结果。
- **能力边界**：实现最简；但输出面向人（表格/着色），Agent 解析脆弱；能力发现性为零（Agent 不知道有哪些子命令与参数）。
- **风险与对策**：解析脆弱（必然/影响中）→ 保留为辅助：所有子命令支持 `--json` 结构化输出。

### Q4-S2 MCP 标准工具协议

- **原理**：stdio 上运行 JSON-RPC，server 以 tools 列表自描述（名称/入参 schema/出参 schema），Agent 侧原生支持发现与调用；工具实现直接复用 daemon 内同一套编排方法。
- **能力边界**：能力范围 = 工具集设计（查历史/执行/检索方案/诊断/会话）；stdio 生命周期由 Agent 管理，长驻数据在 daemon。
- **风险与对策**：协议演进（概率低/影响低）→ SDK（rmcp）随协议升级；安全面（Agent 可执行命令）→ 与人类同闸门同审计，destructive 需显式确认标志。

### Q4-S3 自定义 HTTP API

- **原理**：本地 REST 端点 + token 鉴权。
- **能力边界**：通用性好；但 Agent 生态无自动发现，需逐家适配，且开放端口引入攻击面。
- **风险与对策**：生态弱 + 安全面（必然/影响中）→ v1 不做，v1.1 评估（若做仅绑定 127.0.0.1）。

### Q5-S1 平台原生 shell 适配

- **原理**：daemon 运行于目标平台，检测平台与可用 shell；提案生成时按平台产出语法（POSIX vs PowerShell/cmd），执行时经该平台默认 shell 解释。
- **能力边界**：命令生态即平台生态，无翻译损耗；但同一方案跨平台需按 platform 字段重新生成；PowerShell 与 POSIX 语义差异（管道对象 vs 文本）由提案层吸收，不做运行时翻译。
- **风险与对策**：方言差异导致提案语法错（概率低/影响低）→ 提案标注 platform，方案库按平台过滤；转义陷阱（引号/路径）→ 生成层统一转义规则。

### Q5-S2 内嵌统一工具集

- **原理**：自带一套跨平台核心工具实现（文件/文本/进程），屏蔽平台差异。
- **能力边界**：语义完全可控；但工程量巨大（重写 coreutils 子集）、与系统真实生态割裂（用户还是要面对原生工具）、二进制膨胀。
- **风险与对策**：投入产出比极低（必然）→ 不采用。

### Q6-S1 文件系统快照（v2 预研）

- **原理**：借助 btrfs/LVM/overlayfs 在块或挂载层做快照，回滚即恢复快照。
- **能力边界**：完整且强一致；但平台碎片化严重（btrfs 仅部分发行版、Windows 需 VSS、macOS 需 APFS 快照），对普通目录不可用，root 权限要求高。
- **风险与对策**：平台覆盖碎片化（必然）→ 仅作为特定平台的增强，不作主路径。

### Q6-S2 dry-run + 逆向命令知识（评审后废弃）

- **原理**：为可逆命令预置"执行 → 撤销"映射（`touch f` → `rm f`），回滚执行逆向序列。
- **能力边界**：命令级精细、无需特权；但映射覆盖有限，不可逆命令无解。
- **废弃原因（2026-10-11 评审）**：逐命令维护逆向映射 = 永远做不完的"判断机制"；S4 效果日志以统一机制覆盖全部文件效果，使其冗余。

### Q6-S3 git 工作区快照（评审后废弃，不引入 git）

- **原理**：对受管工作目录自动 `git init`，危险命令执行前 commit 基线到独立 refs，回滚 = revert。
- **能力边界**：只覆盖 git 仓库内文本工作树；`/etc`、二进制、目录外副作用不覆盖；恢复语义要求用户懂 git；对未提交工作树的恢复粗糙。
- **废弃原因（2026-10-11 评审两轮定稿）**：① 覆盖面与恢复语义均不及 S4；② 用户明确要求回滚链路不引入任何 git 依赖——快照仓库为纯 Rust 自实现的内容寻址存储（思想与 git 对象模型同构，属存储结构而非 git 技术，零 git 组件/命令/格式依赖）。

### Q6-S4 效果日志（回滚日志）——评审采纳方案

- **原理**：不判断命令可逆性，统一两步走。**执行前**：按捕获范围（cwd 子树 + 命令显式路径参数 + 影响面分析输出，为统一策略非逐命令判断）将文件**前像**写入内容寻址快照仓库（去重+压缩；小文件全量复制，大文件 reflink/硬链接，超限标记 heavy 仅记路径）；**执行后**：前像 manifest 与现况 diff，生成**效果日志**（每文件一条：路径/op=created|modified|deleted|renamed/before/after），以全局单调 seq 随执行记录入库。**回滚**：`iac rollback` 逐行（seq）倒序回放，支持三种范围语义——`--to <行>`（回滚到指定行，其后全部回放）、`--from <行> [--to <行>]`（从指定行回滚到指定行 / 一直回滚到最远）；遇不可回滚条目按 `--on-conflict <ask|skip|abort>` 逐条决策（可默认跳过），结果计入报告；**文件级**：`iac file history <路径>` 列出该文件全部版本（每次执行一条，标注时间+命令），`restore` 直接替换——"知道恢复到哪个版本、恢复即替换"。**长度控制**：rollback.max_entries 限制执行点数（默认 1024、最大 65536、可配置），与天数/容量 retention 并行，超限清退最旧执行点。
- **能力边界**：只覆盖经 iA 执行的命令与捕获范围内的路径（范围外写入标 out_of_scope 明示）；网络/远程副作用不覆盖（闸门兜底）；有存储成本。
- **风险与对策**：存储膨胀（概率中/影响中）→ 内容寻址去重 + retention（默认 7 天/1GB LRU）+ trash 统一回收（"由系统自动回收"）；执行中长事务窗口（概率低/影响低）→ 前像在执行前已落库，与执行时序解耦。

### Q7-S1 进程内 FFI 引擎

- **原理**：经 llama-cpp-2 将 llama.cpp 链接进 daemon，直接加载 GGUF 权重在进程内推理。
- **能力边界**：无子进程管理、最低调用延迟；但构建链引入 cmake + C++ 工具链，Windows/交叉编译矩阵复杂；引擎崩溃直接拖垮 daemon；二进制体积显著增大。
- **风险与对策**：构建复杂度（概率高/影响中）→ FFI 会使"单命令安装"的发布矩阵翻倍；进程隔离丧失（概率低/影响高）→ 无法轻量恢复。

### Q7-S2 插件化引擎子进程

- **原理**：modelhub 将"引擎二进制（llama-server，OpenAI 兼容端点）+ 模型 GGUF + 清单（sha256/大小/上下文长度）"作为**模型插件包**从 HuggingFace/魔搭下载安装；daemon 以子进程拉起引擎，经同一 AiAdapter 以 OpenAI 兼容协议调用——本地引擎对上层只是又一个 Provider 档案。
- **能力边界**：首次使用需一次下载（数百 MB 级，可换源/镜像）；推理质量受限于小模型；子进程需端口与生命周期管理。
- **风险与对策**：下载失败（概率中/影响低）→ 断点续传 + 多源（HF/hf-mirror/ModelScope）+ 云后端兜底；引擎崩溃（概率低/影响中）→ supervisor 检测重启 + 标记降级；sha256 校验防投毒。

### Q7-S3 依赖外部运行时（Ollama）

- **原理**：不做任何内置，仅把 Ollama 端点作为一种 Provider 档案。
- **能力边界**：零下载实现成本；但"开箱可用"依赖用户自装 Ollama，违背 G12 定位。
- **风险与对策**：开箱不可用（必然）→ 保留为兼容路径，不作为内置方案。

### Q8-S1 静态翻译映射表

- **原理**：内置"源方言命令+参数模式 → 目标方言命令+差异说明"映射数据集，确定性匹配，毫秒级零 AI 成本。覆盖目标为**官方常用命令全集**：POSIX/coreutils/bash 内建 → PowerShell 高频 cmdlet / cmd 内置（数百条量级），随版本发布维护。每条目含**参数级映射**，分四类处理：① 直映（语义与命名皆同）；② 改名/值变换（如 `-r`→`-Recurse`、`-h`→数值格式化差异，逐参数给 note）；③ 无等价（明确标注 + 给最近替代或省略警示）；④ 组合型（该命令不可一对一，转 AI 规划，见 S2）。
- **能力边界**：静态表只能覆盖"有确定等价关系"的部分；方言语义差异（PowerShell 管道传对象 vs 文本）以注释说明而非强行等价；长尾命令与复杂管道超出静态表范围。
- **风险与对策**：官方命令集庞大导致维护负担（概率中/影响中）→ 分层：核心 200~400 条人工维护内置，其余靠 S2 闭环自增长；条目错误（概率低/影响中）→ verified 机制 + 用户确认转正。

### Q8-S2 AI 翻译与组合规划闭环

- **原理**：静态未命中时，携"原命令 + 源/目标方言 + 平台上下文"交 LLM：若可一对一翻译则产出等价命令；**若需命令组合（管道/多命令/脚本），由 AI 规划生成平台化脚本**；两者结果都回写翻译映射（verified=false），组合脚本另存方案库（tags 含 translation/auto）——此后再命中走静态路径，形成"AI 一次、终身静态"的自增长闭环。用户确认后 verified 转正。
- **能力边界**：依赖后端可用性；复杂管道/别名/环境差异翻译质量受限；脚本类产物正确性需执行闸门兜底。
- **风险与对策**：AI 不可用（概率低/影响低）→ 返回原命令与说明不阻塞（AC-19/1301）；缓存污染（概率低/影响低）→ verified 标记 + 用户确认即转正；脚本副作用（概率低/影响中）→ 脚本同样过风险闸门与 dry-run 说明。

### Q8-S3 Shell 包装伪装

- **原理**：把 iac 挂为 shell wrapper/别名拦截全部输入，用户"以为"在用习惯 shell。
- **能力边界**：体验最无缝；但侵入用户 shell 配置、与真实 shell 语义冲突面大（脚本、补全、快捷键），故障面波及一切输入。
- **风险与对策**：侵入性过高（必然）→ v1 不做；其思想在 v1.1 shell 集成 widget 评估。

### Q9-S1 确定性拼接

- **原理**：范围收集（任务段/行号区间的命令序列）→ 按原序拼接 → 注入平台标准头部（sh: `set -euo pipefail`；PowerShell: `$ErrorActionPreference='Stop'`）→ 按目标平台产出 sh / ps·bat 版本。纯函数、可单测、零 AI 成本。
- **能力边界**：脚本质量 = 命令原样（无参数化、无预检）；方言混合的命令序列无法自动适配。
- **风险与对策**：脚本僵硬（必然/影响低）→ 与 S3 精修组合。

### Q9-S2 AI 全代

- **原理**：把范围与意图描述交 LLM 直接产出完整脚本。
- **能力边界**：脚本质量上限高；但引入不确定性、依赖后端、与"记录的是真实执行过的命令"的忠实性冲突（LLM 可能改写命令语义）。
- **风险与对策**：忠实性丢失（概率中/影响高）→ 不采用为默认路径。

### Q9-S3 拼接 + 可选精修

- **原理**：默认 S1；用户显式触发 AI 精修——参数化（路径/值提炼为脚本参数）、依赖预检（命令存在性/目录存在性检查注入）、跨方言适配（混合方言统一）——产出**修订 diff**，确认后覆盖。
- **能力边界**：精修质量依赖模型；diff 确认保证人工在环。
- **风险与对策**：LLM 不可用（概率低）→ 精修不可用但拼接始终可用；误精修（概率低）→ diff 确认 + 原稿保留。

## 5. 结论

- **Q1 → S2 为主、S1 降级兜底**：命令知识 grounding 控幻觉，解析/召回失败自动降级纯 LLM 并标记 unverified；S3 的固化思想并入方案库（确认过的高频提案可转存复用）。
- **Q2 → S1+S2 混合**：通用错误码/模式走静态快速通道（离线即时），其余走 LLM 证据链诊断；LLM 不可用时只剩快速通道并明确告知。
- **Q3 → SQLite(WAL)**：rusqlite bundled，单文件零部署，事务与索引满足 AC-05/07/13/16。
- **Q4 → MCP 为主、`--json` CLI 为辅**：stdio MCP Server 暴露 `iac_` 工具集，与 IPC 共享同一 dispatch；不建 HTTP。
- **Q5 → 平台原生 shell 适配**：提案按 Platform 生成语法，执行经平台 shell；不做内嵌工具集。
- **Q6 → 效果日志（S4）为 v2 回滚主力（2026-10-11 评审定稿）**：不逐命令判断可逆性；执行前统一捕获前像、执行后 diff 成效果日志；回滚 = 逆序回放到任意执行点（point-in-time），单文件版本历史可查可恢复；删除效果先入回收站、retention 统一自动回收。**回滚链路零 git 依赖**（快照仓库为纯 Rust 内容寻址自实现）。S2 逆向命令知识废弃（判断机制冗余）；S3 git 方案废弃（不引入 git）；S1 文件系统快照仍为平台级增强后置。v1 的 `executions.journal_ref` 字段与影响面预览钩子即为此设计。
- **无 git 备选方案盘点（结论：均不优于 S4 主线）**：① OS 原生文件系统快照（btrfs/LVM/APFS/VSS）——覆盖整卷但平台碎片化且需特权，仅作 S1 平台增强后置；② overlay/FUSE COW 沙盒（命令跑在 overlay 上层、回滚=丢层）——Linux-only 且需挂载权限；③ 事件监听抢救（inotify/FSEvents）——事件到达时旧内容可能已被覆盖，前像不可靠；④ syscall 拦截（LD_PRELOAD/dylib）——静态链接可绕过、平台碎片化。
- **Q7 → 插件化引擎子进程（S2）**：modelhub 从 HF/魔搭（含镜像）下载"llama-server 引擎 + GGUF 模型"插件包（sha256 校验），daemon 子进程拉起后经同一 AiAdapter 以 OpenAI 兼容协议调用——本地引擎即一个 Provider 档案（local-builtin）；Ollama（S3）保留为兼容档案。FFI（S1）v1 不做，构建矩阵与进程隔离是主因，v2 再评估。
- **Q8 → 静态映射表（S1）为主 + AI 翻译/组合规划（S2）兜底闭环**：静态表覆盖官方常用命令全集（核心条目人工维护、随版本发布）并含参数级四类映射；一对一不可译时 AI 规划组合生成脚本，确认后"入库（方案库）+登记映射"，此后零 AI 成本；翻译结果一律以提案呈现、确认后执行；S3 包装伪装 v1 不做。
- **Q9 → 拼接 + 可选精修（S3）为脚本工坊机制（2026-10-11 评审新增，痛点 3）**：默认确定性拼接（零 AI、忠实于真实执行过的命令）；AI 精修显式触发、diff 确认、原稿保留。S2 AI 全代否决（忠实性冲突）；脚本命名注册为方案库脚本资产（recipes.kind=script + name 唯一），`iac run @名` 即一条命令，执行过同一闸门并纳入回滚日志。
- 不确定项进入 _03 最终选型：MCP SDK 具体版本、SQLite 驱动特性集（bundled vs system）、LLM 客户端自写 vs 现成库。
