# 01 候选方案原理对比（_02_principle）

> 状态：draft　更新：2026-10-11

## 1. 要解决的原理问题

从 _01 的 18 条 EARS 验收标准出发，提炼出六个需要技术原理支撑的核心问题：

| 编号 | 原理问题 | 对应验收标准 |
|---|---|---|
| Q1 | 自然语言意图如何变成**可信**的命令（控幻觉、控语法漂移） | AC-01/14 |
| Q2 | 命令失败后如何产出**有据可依**的根因分析 | AC-03 |
| Q3 | 全量执行记录/会话/方案库如何本地存储才能支撑检索与并发 | AC-05/07/13/16 |
| Q4 | 外部 Agent 以什么机制接入才能获得与人类同构的能力 | AC-08 |
| Q5 | 跨三平台的命令执行与提案生成用什么机制统一 | AC-14 |
| Q6 | （v2 预研）执行回滚的机制选型 | 痛点 6，v1 留位 |

## 2. 候选方案清单

| 编号 | 方案 | 一句话原理 |

| Q1-S1 | 纯 LLM 直出 | 意图+平台信息直接进 prompt，模型凭记忆输出命令文本 |

## 3. 逐方案原理阐述

### Q1-S1 纯 LLM 直出

- **原理**：prompt = 意图 + 平台/shell 信息 + 少量示例，模型一次补全输出命令文本；输出直接作为提案。
- **能力边界**：实现最薄、冷启动零依赖；但命令正确性完全依赖模型训练记忆。工具版本更迭（flag 改名/废弃）时模型知识漂移；长尾参数组合易出现"语法正确但参数不存在"的幻觉；无法解释"为什么是这个参数"以外的参数来源。
- **风险与对策**：幻觉命令静默失败（概率中/影响中）→ 执行闸门只能拦已知危险模式，拦不住"无害但错误"；版本漂移（概率高/影响低）→ 无解，需 S2 兜底。**结论：只能作为降级路径，不能作为主路径。**

### Q1-S2 LLM + 命令知识 grounding

- **原理**：先经本地命令知识库（对 `--help`/man 文本做结构化解析得到的 ParamSpec 集合，附 AI 补全与人工验证标记）召回目标命令的参数 schema，注入 prompt 约束生成空间；LLM 输出 JSON 结构化提案，经 schema 校验（参数必须在已注册集合内），未命中知识时降级 S1 并把结果标记 unverified。
- **能力边界**：首次遇到陌生命令需一次解析成本（执行 `--help` 或读 man）；解析器对非标准 help 格式覆盖率有限（Go/Cobra 风格、GNU 风格较标准，手工格式参差）；grounding 只约束参数合法性，不保证语义正确（语义仍靠模型）。
- **风险与对策**：help 格式千奇百怪解析失败（概率中/影响低）→ 降级 S1 + 标记 unverified，用户确认即是反馈回路；知识库膨胀（概率低/影响低）→ 按 command+platform 缓存、LRU 淘汰。

### Q1-S3 纯规则模板库

- **原理**：人工维护"意图特征 → 命令模板"映射表，匹配即得命令。
- **能力边界**：确定性 100%、零延迟、零成本；但自然语言开放性使模板覆盖率永远不足，长尾意图全部漏接，维护成本随覆盖线性增长。
- **风险与对策**：覆盖率不足（必然）→ 仅吸收其思想：用户确认过的高频提案可固化复用（与方案库合流），不作为独立机制建设。**结论：不单独采用。**

### Q2-S1 静态错误映射库

- **原理**：对 exit code（127 命令未找到、126 无执行权限、13 权限拒绝…）与高频 stderr 模式（`No such file or directory`、`Permission denied`…）建映射表，命中即出解释。
- **能力边界**：零成本、离线、毫秒级、确定性；但只覆盖"通用错误"，对具体命令语义错误（如 git 冲突细节）覆盖趋零。
- **风险与对策**：覆盖率低（必然）→ 作为确定性快速通道，未命中走 S2。

### Q2-S2 LLM 上下文诊断

- **原理**：诊断 prompt = 失败命令 + 完整 stderr + 退出码 + cwd/平台/shell + 最近 N 条相关执行记录，要求模型输出结构化诊断：根因假设必须引用 stderr 原文片段作证据、给置信度、给修复提案列表。
- **能力边界**：诊断质量上限取决于模型；依赖后端可用性；上下文窗口限制长 stderr（截断保头部+尾部错误行）。
- **风险与对策**：幻觉根因（概率中/影响中）→ 强制"证据引用"结构（无 stderr 引用的假设标记 speculation）、置信度排序；后端不可用（概率低/影响中）→ 降级 S1 快速通道 + 明确报错。

### Q3-S1 SQLite（WAL）

- **原理**：单文件关系库；WAL 模式下读写不互锁（多客户端读 + 单写者），事务保证追加式审计与会话事件的原子性；索引支撑时间/目录/命令多维度检索。
- **能力边界**：个人规模（十万行级）绰绰有余；需要 SQL 与迁移机制；全文检索默认 LIKE，FTS5 可后续启用。
- **风险与对策**：SQL 样板（必然/影响低）→ storage Adapter 提供薄原语，SQL 归属各 data 方法。

### Q3-S2 嵌入式 KV

- **原理**：按 key 读写 value，无服务进程。
- **能力边界**：写入快、嵌入简单；但历史检索需"时间/目录/命令/状态"多条件组合，KV 无二级索引，须自建倒排，等于重写半个数据库。
- **风险与对策**：查询能力缺失（必然/影响高）→ 不采用。

### Q3-S3 JSON 文件集

- **原理**：每记录一个 JSON 文件，目录扫描即查询。
- **能力边界**：零依赖、人可直接看文件；万条级扫描慢、无原子批量写、并发写靠文件锁脆弱、无索引。
- **风险与对策**：规模与并发均不可持续（概率高/影响高）→ 不采用（仅方案库导出格式沿用 JSON 文件）。

### Q4-S1 仅 CLI 文本协议

- **原理**：Agent 以子进程方式调用 `iac` 子命令，从 stdout 文本中解析结果。
- **能力边界**：实现最简；但输出面向人（表格/着色），Agent 解析脆弱；能力发现性为零（Agent 不知道有哪些子命令与参数）。
- **风险与对策**：解析脆弱（必然/影响中）→ 保留为辅助：所有子命令支持 `--json` 结构化输出。

### Q4-S2 MCP 标准工具协议

- **原理**：stdio 上运行 JSON-RPC，server 以 tools 列表自描述（名称/入参 schema/出参 schema），Agent 侧原生支持发现与调用；工具实现直接复用 daemon 内同一套编排方法。
- **能力边界**：能力范围 = 工具集设计（查历史/执行/检索方案/诊断/会话）；stdio 生命周期由 Agent 管理，长驻数据在 daemon。
- **风险与对策**：协议演进（概率低/影响低）→ SDK（rmcp）随协议升级；安全面（Agent 可执行命令）→ 与人类同闸门同审计，destructive 需显式确认标志。

### Q4-S3 自定义 HTTP API

- **原理**：本地 REST 端点 + token 鉴权。
- **能力边界**：通用性好；但 Agent 生态无自动发现，需逐家适配，且开放端口引入攻击面。
- **风险与对策**：生态弱 + 安全面（必然/影响中）→ v1 不做，v1.1 评估（若做仅绑定 127.0.0.1）。

### Q5-S1 平台原生 shell 适配

- **原理**：daemon 运行于目标平台，检测平台与可用 shell；提案生成时按平台产出语法（POSIX vs PowerShell/cmd），执行时经该平台默认 shell 解释。
- **能力边界**：命令生态即平台生态，无翻译损耗；但同一方案跨平台需按 platform 字段重新生成；PowerShell 与 POSIX 语义差异（管道对象 vs 文本）由提案层吸收，不做运行时翻译。
- **风险与对策**：方言差异导致提案语法错（概率低/影响低）→ 提案标注 platform，方案库按平台过滤；转义陷阱（引号/路径）→ 生成层统一转义规则。

### Q5-S2 内嵌统一工具集

- **原理**：自带一套跨平台核心工具实现（文件/文本/进程），屏蔽平台差异。
- **能力边界**：语义完全可控；但工程量巨大（重写 coreutils 子集）、与系统真实生态割裂（用户还是要面对原生工具）、二进制膨胀。
- **风险与对策**：投入产出比极低（必然）→ 不采用。

### Q6-S1 文件系统快照（v2 预研）

- **原理**：借助 btrfs/LVM/overlayfs 在块或挂载层做快照，回滚即恢复快照。
- **能力边界**：完整且强一致；但平台碎片化严重（btrfs 仅部分发行版、Windows 需 VSS、macOS 需 APFS 快照），对普通目录不可用，root 权限要求高。
- **风险与对策**：平台覆盖碎片化（必然）→ 仅作为特定平台的增强，不作主路径。

### Q6-S2 dry-run + 逆向命令知识（v2 预研）

- **原理**：为可逆命令预置"执行 → 撤销"映射（`touch f` → `rm f`；`mv a b` → `mv b a`），执行前预演影响面（文件树 diff），回滚执行逆向序列。
- **能力边界**：命令级精细、无需特权；但映射覆盖有限，不可逆命令（rm、truncate）无解，只适合"可逆命令误用"场景。
- **风险与对策**：覆盖不足（必然）→ 与 S3 组合分层。

### Q6-S3 git 工作区快照（v2 预研）

- **原理**：对受管工作目录自动 `git init`（若未管理），危险命令执行前自动 commit 基线，回滚 = revert 到基线。
- **能力边界**：覆盖文本工作区效果好、机制成熟；二进制大文件与目录外副作用（系统配置、数据库）不覆盖。
- **风险与对策**：覆盖面局限（必然）→ 与 S2 组合；污染用户 git 历史 → 使用独立 refs 命名空间（如 `refs/iac/*`）。

## 4. 原理级对比

| 维度 | Q1: S1 vs S2 | Q2: S1 vs S2 | Q3: S1 vs S2 vs S3 | Q4: S1 vs S2 | Q5: S1 vs S2 |
|---|---|---|---|---|---|
| 正确性/可信 | S2 优：参数合法性可校验 | S2 优：有证据链 | S1 优：事务+索引 | S2 优：结构化自描述 | S1 优：生态零翻译 |
| 性能 | S1 略优（省一次召回） | S1 优（毫秒级） | S1 优 | — | S1 优 |
| 实现复杂度 | S2 高（解析器+校验） | S2 低（复用 AI 通道） | S3 最低，S1 中 | S1 最低 | S1 远低于 S2 |
| 可演化性 | S2 优：知识库可持续积累 | S2 优 | S1 优（FTS5 演进） | S2 优（协议生态） | S1 优 |
| 风险 | S1 幻觉不可控 | S2 幻觉可约束 | S2/S3 规模不可持续 | S1 解析脆弱 | S2 工程黑洞 |

## 5. 结论

- **Q1 → S2 为主、S1 降级兜底**：命令知识 grounding 控幻觉，解析/召回失败自动降级纯 LLM 并标记 unverified；S3 的固化思想并入方案库（确认过的高频提案可转存复用）。
- **Q2 → S1+S2 混合**：通用错误码/模式走静态快速通道（离线即时），其余走 LLM 证据链诊断；LLM 不可用时只剩快速通道并明确告知。
- **Q3 → SQLite(WAL)**：rusqlite bundled，单文件零部署，事务与索引满足 AC-05/07/13/16。
- **Q4 → MCP 为主、`--json` CLI 为辅**：stdio MCP Server 暴露 `iac_` 工具集，与 IPC 共享同一 dispatch；不建 HTTP。
- **Q5 → 平台原生 shell 适配**：提案按 Platform 生成语法，执行经平台 shell；不做内嵌工具集。
- **Q6（v2 预研倾向，v1 仅留设计位）**：git 工作区快照（S3，独立 refs 命名空间）打底 + 逆向命令知识（S2）做命令级精细撤销，文件系统快照（S1）作为平台增强后置。v1 的 `executions.pre_snapshot_ref` 字段与影响面展示钩子即为此设计。
- 不确定项进入 _03 最终选型：MCP SDK 具体版本、SQLite 驱动特性集（bundled vs system）、LLM 客户端自写 vs 现成库。
