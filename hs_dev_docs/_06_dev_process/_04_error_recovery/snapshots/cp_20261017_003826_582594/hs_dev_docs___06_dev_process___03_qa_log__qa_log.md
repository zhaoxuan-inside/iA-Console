## 问题与答复

### Q0. 「重头进行本项目的开发」的起点与旧产物处置（开场裁决）

- **题域**：范围 / 基线
- **题干**：现有代码、文档（`_00~_10`）、已安装 v0.1.0 是否保留？未提交的 v2 进行中改动如何处理？
- **选项与利弊**：
  - A：纳管存量 + 正式续做（保留现有成果，REVERSE 纳管后继续）
  - B：v0.1.0 冻结，完整重走 BUILD 0→6 做下一版本
  - C：彻底从零重建（破坏性，丢弃现有代码与文档）
- **开发者答复**：C —— 彻底从零重建（破坏性）；未提交改动选「暂时搁置」（不动文件，先做文档/流程层，实施前按流程决定处置）
- **采纳决策**：新开发基线从零建立；旧代码/文档仅作参考事实，不作为新基线；工作区文件在实施阶段裁决前一律不动。
- **关联落盘**：本计划 `_01_plan_log/iaconsole-rebuild_plan.md`；新文档体系 `hs_dev_docs/`（2026-10-16 初始化）。

### Q1. 重建动机与本次验收目标（O2#1）

- **题域**：产品价值 / 过程纪律
- **题干**：为什么从零重建？期望这次「不一样」的是什么？
- **开发者答复**：**之前的需求沟通不够细致，导致最终的实现完全不符合预期。**
- **采纳决策**：本轮 discovery 以「可验收的细节」为冻结门槛——逐能力场景走查、线框/原型确认、每条需求钉到 Given/When/Then 级断言，并由开发者逐项签认；不得用行业常识脑补业务边界。
- **关联落盘**：计划目标段；后续 PRD/vibe_spec 元数据纪律。

### Q2. v0.1.0 不符预期的典型例子（取证）

- **题域**：产品价值 / 交互体验
- **题干**：期望 vs 实际 的典型例子？
- **开发者答复**：
  1. **功能没有实现 AI 驱动命令的核心思想**；
  2. **UI 特别糟糕，交互存在大量问题；例如：抖动。**
- **采纳决策**：这两条定为重建的头号验收主题——① 核心思想必须在主交互中被真实兑现（第三轮起逐场景深挖）；② UI/交互质量须建立可验收的交互标准清单（第二轮末尾深挖取证）。
- **关联落盘**：本日志；后续 PRD 的「验收主题」章。

### Q3. 重建目标范围

- **题域**：范围裁剪
- **开发者答复**：**全量一步到位**——旧产品全部能力（含 GUI、v2 回滚/脚本工坊）一次性钉细并重建。
- **采纳决策**：需求分母 = 全量能力域；需求钉细按能力域逐块深挖（旧 `_01_business` 23 US/46 AC 仅作素材与查漏底稿，逐项由开发者重新确认/修正/重写）。
- **关联落盘**：本计划「范围」段、`_01_product_vision/_02_phased_roadmap`（后续创建）。

### Q4. 首做产品形态

- **题域**：产品形态
- **开发者答复**：**双形态同步推进**——GUI（独立窗口）与 CLI/TUI 两条形态都作为一等交付。
- **采纳决策**：架构上必须让双形态共享同一内核与契约；不接受一形态先行、另一形态「后补」的降级路径。隐性预期：两形态能力对齐、行为一致。
- **关联落盘**：`_03_architecture_design`（阶段 2）、本计划。

### Q5. 平台范围

- **题域**：范围 / 约束
- **开发者答复**：**三平台全支持**——Linux/macOS/Windows 全部 v1 落地。
- **采纳决策**：跨平台为硬约束（影响选型、打包、CI 与验收方式）；验证资源问题在第二轮 Q4 落实到具体设备环境。
- **关联落盘**：`_00_project_foundation/_03_decision_record`（阶段 1）、本计划。

### Q6. 节奏与时间箱

- **题域**：过程纪律
- **开发者答复**：**质量优先、不设硬时间箱**。
- **采纳决策**：按阶段推进，每阶段交付可用增量与验收物；需求未冻不进入实现；拒绝为赶工批准未验证的降级。
- **关联落盘**：本计划「目标/范围」段。
